# Android cache controls audit

November 23, 2026. Compared Android 0.1.27 (build 28) and the current working tree with the production dashboard. Durations below are shipped defaults unless marked as fixed. The audit used local code, offline tests and read-only Vercel requests. It made zero Mobilism requests.

## Audit priorities

Items 1, 2 and 5 now have controls in the working tree. The remaining gaps retain their order below. See [cache lifetimes and resets](remote-controls.md#cache-lifetimes-and-resets) for defaults and rollout requirements.

Ranked by the feature that can break and the number of Mobilism requests one failure can trigger. The traffic rankings reflect the code paths. Production savings have not been measured.

| Priority | Gap | Why it ranks here |
| --- | --- | --- |
| 1 | Latest, Top and Home release lists | These are primary browsing screens. A bad cached list can affect everyone opening that section. One filtered refresh can read several pages. Make the Home and disk layers honor the same targeted expiry or reset, applied on the next visit. |
| 2 | Followed App Cache retention and eviction | When a frequently followed app drops out of Vercel, multiple phones can independently search Mobilism for it. Use actual misses and fallback searches to tune retention and protect high-demand entries. Keep the existing Mobilism limits. Capacity and eviction can be adjusted on Vercel. |
| 3 | Release category catalog | A stale catalog can give users incorrect filters across Home, Latest and search for the whole app session. One catalog refresh per visibility setting can repair all three surfaces. |
| 4 | Member identities and avatar files | The dashboard cannot correct a known stale avatar or badge during the 30-day minimum. A broad flush could trigger a profile request for each visible author plus image downloads. Keep the long default and invalidate one member when possible. |
| 5 | Premium provider host catalogs | Stale host support can misroute a download or hide a working provider. Add an age limit and a per-provider refresh while retaining account and host verification. |
| 6 | Discussion activity | Opening the category list can trigger a topic-list read for each visible nonempty forum. The independent five-minute hold limits that traffic but ignores the dashboard setting. Coordinate the two lifetimes and keep concurrency bounded. |
| 7 | PM inbox, release comments and direct links | Stale messages and replies are visible to users, but the caches already expire after one minute and user refresh or local writes can invalidate entries. Keep inbox and comment controls separate. |
| 8 | Targeted reset for search and discussion responses | Lifetimes already reach zero. A reset for one affected cache would keep unrelated results warm during incident recovery. |
| 9 | Reaction and navigation metadata | Old fallback data can show an incorrect thumbs-up or retain unused post IDs and page offsets. Bound retention locally and keep correct IDs reusable. |
| 10 | Latest-feed removal evidence and GitHub update metadata | Feed history is already limited to 20 IDs and 24 hours. GitHub update checks do not contact Mobilism. Neither calls for an urgent dashboard control. |

**Applies to every priority.** Remote settings have to reach the phone before they can take effect. Ship conservative client defaults and define what each switch does when Vercel is unavailable. Invalidate on the next normal use, preserve request pacing and server `Retry-After`, and keep follows, credentials, drafts and downloads outside cache resets.

## Fixed in the Android working tree

- Search now preserves valid results when unrelated settings change. Each discussion response uses the lifetime for the page being requested. Changing the debrid interval or Following batch size keeps both caches warm. [Search policy](../core/data/src/main/java/org/mobilism/material/data/SearchRequestPolicy.kt) · [Read policy](../core/data/src/main/java/org/mobilism/material/data/ReadRequestPolicy.kt)
- The app validates release searches, discussion searches, category lists and topic lists before storing them. Malformed results enter a cooldown. A later user visit or retry can make one paced request after the cooldown and any server wait. A valid empty result still counts as a successful response. [API reader](../core/data/src/main/java/org/mobilism/material/data/MobilismApi.kt)
- A freshly posted discussion reply stays visible while the forum catches up. When a server page contains its ID, the app drops the local copy. Later edits and deletions are reflected on refresh, with no extra lookups. [Discussion comments](../app/src/main/java/org/mobilism/material/ui/DiscussionsViewModel.kt)

## Following and other retained data at the time of the audit

- **Followed App Cache.** The dashboard already controls the Vercel lookup interval, batch size, manual cooldown and pull-to-refresh. A batch size of zero disables shared-cache use. The separate Mobilism fallback limits still apply. The server’s 1,000-app capacity, 500 newest slots, demand ranking for the remaining slots, 24-hour retention and 6-hour freshness checks are set in code. Changing storage or eviction policy requires a Vercel deployment today. Android independently rejects snapshots older than 6 hours or larger than 500 returned items. Those client limits require an Android change to raise. [Dashboard controls](../services/daily-usage/src/controls.jsx) · [Cache page](../services/daily-usage/src/following-cache.jsx) · [Lookup](../services/daily-usage/lib/follow-lookup.js) · [Android reader](../core/data/src/main/java/org/mobilism/material/data/LatestAppsClient.kt)
- **Reactions and navigation.** The phone persists the account’s last known thumbs-up when a release response omits it, along with public original-post IDs for likes. Neither disk store has a time or count limit. Forum routing also retains post IDs, pagination offsets and discovered announcement forum IDs in memory. These have no dashboard controls. Category pagination keeps retry buffers so a failed scan can resume without fetching the same pages again. [Repository](../core/data/src/main/java/org/mobilism/material/data/DefaultMobilismRepository.kt) · [Forum IDs](../core/data/src/main/java/org/mobilism/material/data/MobilismApi.kt)
- **Avatar image files.** The avatar component passes an ordinary image URL to Coil. In the working tree, the release-artwork switch applies to requests tagged as release artwork or served by `images.mobilism.org`. Avatars served elsewhere have no equivalent control. The release-artwork switches were absent from the production dashboard bundle at the time of the audit. [Avatar loader](../app/src/main/java/org/mobilism/material/ui/MessageAvatar.kt) · [Image cache policy](../app/src/main/java/org/mobilism/material/images/AppImageLoader.kt)
- **Cache maintenance and updates.** The phone retains up to 20 Latest feed IDs for 24 hours to corroborate a removal. The GitHub updater uses a fixed 12-hour automatic check interval and keeps the last known update. The dashboard configuration itself normally refreshes after 5 minutes, expires after 15 and falls back to shipped defaults on cold start or a failed fetch. A future emergency switch inherits those delivery limits unless its persistence is designed explicitly. [Feed baseline](../core/data/src/main/java/org/mobilism/material/data/LatestFeedWindow.kt) · [GitHub updater](../app/src/main/java/org/mobilism/material/updates/AppUpdateChecker.kt) · [Controls reader](../app/src/main/java/org/mobilism/material/remote/RemoteControlStore.kt)

**Verification.** The original audit reproduced both cache bugs using local loaders. After the fixes, 560 Android unit tests passed and three live-service tests were skipped. All 13 selected emulator tests passed with networking disabled, including the repository request-count checks and discussion posting and deletion paths. Verification made zero Mobilism requests.
